## 一、Redis 的使用场景

### 问 1：分布式系统中如何解决 session 共享问题？

如果后端服务部署在多台服务器上，用户第一次请求被分配到服务器 A，session 存在 A 上；第二次请求被分配到服务器 B，服务器 B 无法获取服务器 A 上的 session 数据，用户需要重新登录。

**解决方案**：使用一个"公共存储区域"，所有服务器都能访问 —— 这就是 Redis 的核心使用场景之一。

```
用户登录 → Session 存入 Redis → 任意服务器都能从 Redis 读取
```

## 二、高性能的原因

### 问 4：Redis 为什么比硬盘数据库快？

**纯内存存储**是 Redis 高性能的核心原因。

```
内存读写：约 100ns 级别
硬盘读写：约 10ms 级别（相差约 10 万倍）
```

## 三、持久化策略

### 问 5：Redis 断电后数据会怎样？

内存是**易失的**，断电后数据会丢失。Redis 提供两种持久化方案：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **RDB 快照** | 每隔一段时间把内存数据打包存到硬盘 | 简单，恢复快 | 可能丢失间隔内的数据 |
| **AOF 日志** | 每次写操作都同步写入硬盘 | 数据不丢失 | 硬盘 IO 成为瓶颈 |
| **混合持久化** | RDB 快照 + AOF 日志结合 | 兼顾速度和完整性 | 配置复杂 |

**混合持久化（推荐）**：

```
┌─────────────────────────────────────────────────────────┐
│                    混合持久化                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  RDB 快照（每 5 分钟）                                   │
│  ├── 保存完整数据快照                                    │
│  └── 用于快速恢复 + 备份                                 │
│                                                         │
│  AOF 日志（每秒刷盘）                                    │
│  ├── 记录两次快照之间的写命令                            │
│  └── 用于数据完整性                                      │
│                                                         │
│  重启恢复流程：                                          │
│  1. 加载最近的 RDB 快照（快速）                          │
│  2. 回放 RDB 之后的 AOF 命令（完整）                     │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

---

### COW 机制（Copy-On-Write）

RDB 快照期间，Redis 使用 **COW（写时复制）** 机制，不阻塞写操作：

```
第 5 分钟：开始 RDB 快照
├── Redis fork() 一个子进程
├── 子进程：拥有内存的"快照"（只读）
└── 主进程：继续处理写请求
    ├── 修改数据时，复制要修改的页
    └── 原数据页保持不变（供子进程读取）
```

**类比前端**：

```js
// 浅拷贝 - 类似 COW
let original = { a: 1, b: 2 }
let snapshot = { ...original }  // 快照

// 修改原对象
original.a = 999  // 不影响快照
// snapshot.a 仍然是 1
```

## 四、核心数据结构

Redis 有 5 种核心数据结构，每种都对应前端的某种概念。

### String（简单值存储）

```bash
SET username "zhangsan"
GET username
```

**典型场景**：缓存简单值、Session 存储、分布式锁（`SETNX`）

---

### Hash（对象存储）

```bash
# 设置字段
HSET user:1001 name "zhangsan"
HSET user:1001 email "zhang@example.com"
HSET user:1001 age 25

# 获取单个字段（类似 user.name）
HGET user:1001 name

# 获取所有字段（类似 Object.entries(user)）
HGETALL user:1001
```

**典型场景**：存储用户信息、商品详情等"对象"类型数据

---

### List（队列场景）

```bash
# 从尾部插入
RPUSH queue "msg1" "msg2" "msg3"

# 从头部取出（先进先出）
LPOP queue
```

**典型场景**：消息队列、任务队列、最近浏览记录

---

### Set（去重场景）

```bash
# 添加元素（重复添加会自动忽略）
SADD tags "js" "vue" "redis"

# 集合运算
SINTER set1 set2    # 交集（共同好友）
SUNION set1 set2    # 并集（合并标签）
SDIFF set1 set2     # 差集（互粉检测）
```

**典型场景**：标签系统、共同好友/共同关注、抽奖

---

### ZSet（排行榜场景）

```bash
# 添加元素（带分数）
ZADD leaderboard 100 "player1"
ZADD leaderboard 300 "player2"
ZADD leaderboard 200 "player3"

# 直接获取前 3 名（已排序）
ZREVRANGE leaderboard 0 2 WITHSCORES
```

**典型场景**：游戏排行榜、热门文章、优先级队列

---

### 数据结构对比

| 数据结构 | 前端类比 | 典型场景 | 核心命令 |
|----------|----------|----------|----------|
| **String** | `const name = "xxx"` | 缓存简单值、session | `SET`/`GET` |
| **Hash** | `Object` | 存储对象（用户信息） | `HSET`/`HGET`/`HGETALL` |
| **List** | `Array`（push/shift） | 消息队列、任务队列 | `RPUSH`/`LPOP` |
| **Set** | `Set` | 标签、共同好友（去重） | `SADD`/`SINTER`/`SUNION` |
| **ZSet** | 带权重的 Map | 排行榜、优先级队列 | `ZADD`/`ZREVRANGE` |

## 五、缓存读写策略

### 读取缓存

```
用户请求 → 先查 Redis → 命中则返回
          ↓ 未命中
        查数据库 → 写入缓存 → 返回
```

### 删除缓存策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **删除缓存** | 修改 DB 后删除缓存 | 简单可靠 | 下次访问会慢 |
| **更新缓存** | 修改 DB 后更新缓存 | 下次访问快 | 并发冲突风险 |
| **自动过期** | 设置过期时间 | 无需手动删除 | 过期前数据不一致 |

**推荐**：**删除缓存 + 自动过期**组合

## 六、缓存三大问题

### 缓存穿透

恶意用户访问**不存在**的商品 ID，缓存和数据库都没有，每次请求都打到数据库。

**解决方案**：
```bash
# 把"空结果"也缓存起来
SET product:999999 "NULL" EX 60
```

其他方案：布隆过滤器（Bloom Filter）、参数校验

---

### 缓存击穿

热门商品缓存突然过期，大量并发请求同时打到数据库。

**解决方案**：

- **互斥锁**：只允许一个请求去数据库查询，其他请求等待
- **永不过期**：设置"逻辑过期"，后台定时任务异步更新

---

### 缓存雪崩

大量 key 同时过期或 Redis 宕机，所有请求打到数据库。

**解决方案**：
1. **过期时间随机化**：`expire = base + random(1, 300)`
2. **Redis 集群**：多台互为备份
3. **限流降级**：数据库压力大时限制请求

## 七、集群架构

### 主从复制

```
       主节点 (Master)
      /    |    \
   从 1    从 2    从 3
```

- 主节点负责**写**，从节点负责**读**（读写分离）
- 主节点挂了 → **无法写入**（需要人工干预切换）

---

### 哨兵模式（Sentinel）

```
       哨兵 1    哨兵 2    哨兵 3
          |       |       |
          v       v       v
       主节点 → 从节点 1 → 从节点 2
```

哨兵的作用：
1. **监控**：不断检查主节点和从节点是否健康
2. **通知**：主节点挂了，通知管理员
3. **自动故障转移**：投票选举一个新主节点

**Quorum（多数派原则）**：至少 `(N/2 + 1)` 个哨兵同意，才能判定主节点挂了。哨兵数量必须是奇数（避免脑裂）。

---

### 分片集群（Redis Cluster）

Redis 使用 **哈希槽（Hash Slot）** 来分配数据：

```
┌─────────────────────────────────────────────────────────┐
│              Redis Cluster (16384 个槽)                  │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  节点 A: 槽 0 ~ 5000                                    │
│  节点 B: 槽 5001 ~ 10000                                │
│  节点 C: 槽 10001 ~ 16383                               │
│                                                         │
│  存数据：CRC16(key) % 16384 → 定位到槽 → 定位到节点      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

---

### 集群架构对比

| 架构 | 节点数 | 容量 | 高可用 | 复杂度 | 适用场景 |
|------|--------|------|--------|--------|----------|
| **单机** | 1 | 16GB | ❌ 无 | 低 | 开发/测试 |
| **主从** | 1 主+N从 | 16GB | ⚠️ 需手动切换 | 中 | 读多写少 |
| **哨兵** | 1 主+N 从+M 哨兵 | 16GB | ✅ 自动切换 | 中高 | 高可用要求 |
| **集群** | 3+N 分片 | N×16GB | ✅ 自动切换 | 高 | 大规模数据 |

## 总结

| 概念 | 关键点 | 类比前端 |
|------|--------|----------|
| **使用场景** | 分布式 session 共享、缓存 | 全局状态管理（Vuex/Pinia） |
| **高性能** | 纯内存存储 | Map 比数组遍历快 |
| **持久化** | RDB + AOF 混合 | localStorage 定时保存 |
| **数据结构** | 5 种类型，各有所长 | String/Object/Array/Set |
| **缓存问题** | 穿透/击穿/雪崩 | 缓存层级防御 |
| **主从复制** | 主写从读，读写分离 | CDN 边缘节点 |
| **哨兵模式** | 监控 + 自动故障转移 | 健康检查 + 负载均衡 |
| **分片集群** | 16384 哈希槽，数据分散 | 分治思想 |
